An agent task may use the `run_js` tool to execute an ES module with top-level await. Each invocation runs in a fresh owned JavaScript runtime with a new global scope and module cache. Relative imports from the virtual entry resolve from the execution's configured working directory; file-backed modules resolve relative imports from their importing module. import.meta.url is the module's file URL or final HTTP/HTTPS URL; the virtual run_js entry uses a synthetic <virtual-entry>.mjs file URL under its cwd, not an existing source file.

Available runtime APIs depend on the selected profile. The `noe:docs` module describes the full API catalog, including APIs that are not enabled in a particular profile. Host-specific runtime facts report HTTP/HTTPS ESM URL import availability; remote modules resolve relative imports against their own URLs. URL import and fetch are independent capabilities.

The `run_js` result reports stdout, stderr, exit code, and execution reason. The complete model-facing result JSON, including metadata, JSON escaping, data, diagnostics, and hook results, has a default 65536-byte budget. For necessary larger output, put `// @noe: {"outputBytes": 131072}` after the operation comment in the initial line-comment block (integer range 1024–262144 bytes). This same setting controls stdout/stderr capture; console output and default-export data use the same output budget. Each stream retains its beginning and end when truncated. Oversized model-facing results become incomplete `outputPreview` text with `outputLimit` byte counts and original execution status. Narrow searches or return filenames/counts. Do not blindly replay side effects to retrieve output. `NOE_CONTEXT_STATUS` is a user message in conversation history. It may include factual notices of recovered hook failures, not human steering or repair commands. Such failures do not themselves stop the task or require another model request. Optional `TaskOutcome.hookFailures` preserves them, including final-response failures that the model may never receive; `includeAnswer:false` keeps those records and `read_task_result` reads only the unchanged answer.

The `noe:agent` module exposes `run_agent`, `spawn_agent`, `observe_agent`, `queue_agent`, `wait_task`, `wait_tasks`, `read_task_result`, `steer_agent`, `cancel_task`, `stop_agent`, and `list_models`. Agent and task operations are checked against the current execution's ownership scope. `spawn_agent` and `queue_agent` return accepted command identifiers; `wait_task` observes one command's retained result. `cancel_task` cancels one command, while `stop_agent` stops an instance and its remaining work.

For a parent waiting on delegated work, prefer one `wait_tasks({tasks: [{agentId, commandId}, ...], includeAnswer: false})` call for the whole set instead of polling or Promise.all of completion-only waits. It returns `{reason: "completed" | "steer", runId?, completed: [{agentId, outcome}], pending: [{agentId, commandId}]}`. A steer return leaves children running and guidance pending for the normal next model boundary. Return/export the result and end this run_js so the parent model can read the guidance and decide what to do; do not immediately re-wait in the same tool. Use wait_task when completion-only waiting is intentional. Request/owner cancellation rejects rather than reporting a steer.
