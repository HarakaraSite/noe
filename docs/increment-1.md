> この文書は実装当時の計画・検証記録です。現在の仕様は[APIリファレンス](api.md)と[stdlib移行記録](increment-12.md)を参照してください。旧`noe.*` API、独自I/O実装、当時の対象外・中断動作は現行仕様ではありません。

インクリメント1で、[MVP案](mvp.md)のJavaScript実行・ローカルモジュール・ファイル処理・HTTP取得を実装する。5つのスライスを順番に進め、各スライスで動く機能を確認する。

状態は完了。全5スライスの実装・テスト・レビューと、インクリメント全体の総合E2Eテストを完了した。

## 実装方針

- NOE本体、CLI、ホストAPIはGoで実装する。JavaScriptエンジンはgo-quickjsを使う。
- go-quickjsの依存バージョンを固定する。`_refs/go-quickjs`は参照用途とし、製品コードの依存先にしない。
- npm対応、Node互換、Deno互換は実装しない。Web標準は必要なサブセットだけを提供する。
- REPL、TypeScript対応はインクリメント1に含めない。
- 実行対象は、自分が用意したローカルのスクリプトを想定する。
- ソース読み込みとエンジンでの実行を分ける。将来用の複雑な拡張機構は作らない。

## 公開API

実行環境とファイル操作は、小さなグローバルオブジェクト`noe`にまとめる。インクリメント1では、以下のAPIを採用する。

```js
noe.args                         // スクリプトに渡した引数
noe.env.get("NAME")               // 未設定ならundefined
noe.cwd()                        // カレントディレクトリ
noe.exit(0)                      // 実行を終了
await noe.readTextFile("in.json")
await noe.writeTextFile("out.json", text)
```

`console.log`・`console.warn`・`console.error`と`fetch`はグローバルに置く。提供するサブセットを利用説明に明記する。

`noe.args`はスクリプトに渡した引数だけを含め、実行ファイル名やスクリプト名は含めない。`eval`では空配列とする。ファイルの読み書きは`Promise<string>`・`Promise<void>`を返す。

## スライス1 CLIからJSを実行する

GoモジュールとCLIを作り、go-quickjsを接続する。

- `noe run script.js [args...]`、`noe eval 'コード'`、help、versionを提供する。
- `run`と`eval`はESモジュールとして評価する。ローカルimportの対応はスライス2で追加する。
- consoleの3メソッドを提供する。`log`は標準出力、`warn`・`error`は標準エラーに出す。
- ソースのファイル名をエンジンに渡し、構文エラーと実行エラーに位置・スタックを表示する。
- 正常終了と失敗時の終了コードを返す。

完了条件は、Hello Worldをファイルと`eval`の両方で実行でき、壊れたコードでは診断と非ゼロ終了コードが得られること。CLIの基本経路とconsoleの出力先を確認する。

## スライス2 ローカルモジュールと非同期実行

スライス1の評価経路に、モジュールローダーとジョブ処理を接続する。

- `./`・`../`から始まり、拡張子を明示したローカルJSを読み込む。
- import元のファイルを基準にパスを解決する。
- `eval`はcwdに位置する仮想エントリーモジュールとして扱い、相対importはcwd基準とする。
- Promise、`async/await`、top-level awaitを扱う。
- 開始したホストI/Oと、その結果から生じるJS処理の完了を待つ。
- 未処理のPromise rejectionを報告し、失敗時は非ゼロで終了する。
- go-quickjsの`rt.Go`とジョブ処理APIを使う。JSランタイムの操作は一つのgoroutineに集約し、I/O側にはGoの値を渡す。

エントリーモジュールの評価完了と、残っているI/O・ジョブの有無を別に判定する。`EvalModule`は非同期の評価が未完了でも名前空間を返し、`Busy`だけではモジュールの評価完了を判定できない。

スライス2で、評価経路を小さな内部起動コードに切り替える。`EvalFile`で以下のようにエントリーを動的importし、返されたPromiseを`Await`する。`run`では読み込んだファイル、`eval`では単一の仮想エントリーを既存ローダーに渡す。

```js
(() => {
  const p = import("./entry.js");
  p.catch(() => {});
  return p;
})()
```

先に付ける`catch`はエントリーの失敗を二重報告しないためのもので、元のPromiseの失敗は`Await`から診断する。解決する処理が残っていない未完了の評価は、`ErrNeverSettles`を実行失敗として扱う。エントリーの評価完了後も、`Busy`・`Wake`・`RunJobsContext`で開始済みI/Oと後続のJS処理を実行する。

完了条件は、別ディレクトリのモジュールを読み込めること。テスト用の非同期ホスト処理で、成功・失敗とも完了まで処理されること。I/O完了待ちと、待機後のエラーが終了コードに反映されることを確認する。`await new Promise(() => {});`を成功終了として扱わないこと、エントリー完了後に残るI/Oも実行することを確認する。

## スライス3 引数と環境変数とファイル処理

スライス2の非同期実行を使い、`noe` APIを実装する。

- `noe.args`、`noe.env.get`、`noe.cwd`、`noe.exit`を提供する。
- テキストファイルの読み書きを非同期APIとして提供する。
- ファイル操作の相対パスはcwd基準とする。importの相対パスはimport元基準のままとする。
- ファイル操作の失敗はPromiseのrejectとして返す。
- `noe.exit`は実行を止め、ランタイムを片付け、CLIに終了コードを返す。ホストAPIから直接`os.Exit`を呼ばない。

`noe.exit(code)`はランタイム外のGo状態に終了要求とコードを記録してから、ランタイムを操作しているgoroutine上で`Close`する。その要求に伴う`ErrClosed`は通常の実行失敗と区別し、指定したコードで終了する。終了要求のない`ErrClosed`を成功扱いしない。

通常終了では開始済みI/Oを待つ。明示的な`noe.exit`では、後続のJSや`catch`・`finally`を実行せず、停止を優先する。`Close`によるcontextのキャンセルと、I/Oのgoroutineが終了したことを同一視しない。終了後のJSランタイムにはI/O側から触れない。

完了条件は、引数で渡したJSONファイルを読み、加工して保存できること。環境変数の参照と指定した終了コードも確認する。ファイルの読み書き失敗がスクリプトに伝わり、未処理の場合は失敗終了することを確認する。`noe.exit(0)`と非ゼロの明示終了を、トップレベルと非同期処理の継続部分から確認する。

## スライス4 HTTPのサブセット

Goの`net/http`に接続し、必要な範囲の`fetch`を実装する。

```js
const response = await fetch(url, {
  method: "POST",
  headers: { "Content-Type": "application/json" },
  body: JSON.stringify(data),
});

console.log(response.status);
const result = await response.json();
```

- 入力はURL文字列、GET・POST、文字列値のヘッダー、文字列のbodyを対象とする。
- メソッド省略時はGETとする。bodyはPOSTで提供する。対応するオプションは`method`・`headers`・`body`とし、未対応のオプションや入力形式はエラーとして返す。
- レスポンスは`status`・`ok`・`text()`・`json()`を提供する。
- `text()`は`Promise<string>`、`json()`はJSONを解析した値のPromiseを返す。JSONの解析失敗はrejectする。一括取得したbodyを保持し、これらのメソッドは繰り返し呼べるサブセットとする。
- bodyは一括取得する。ストリームやWeb標準API一式は導入しない。
- HTTPの4xx・5xxはレスポンスとして返し、通信失敗はrejectする。
- I/Oの実行中にJSランタイムを別goroutineから操作しない。
- HTTPリクエストには`rt.Go`が渡すcontextを使い、レスポンスbodyはI/Oのgoroutine内で閉じる。

完了条件は、GoのローカルテストサーバーでGET・POST、テキスト・JSON取得、HTTPエラーステータス、通信失敗を確認できること。取得結果をファイルに保存できること。外部サービスをテストの前提にしない。

## インクリメント全体の検証結果

Go 1.27.2、Linux amd64環境で次の検証が成功した。

- スライス1〜4で`go test ./...`と`CGO_ENABLED=0 go build -o /tmp/noe-increment-1 ./cmd/noe`を実行した。スライス5ではREADMEの実例を含むCLI E2Eを実行した。

- 全スライスのレビュー後に`go test -tags=e2e ./... -count=1 -v`を実行し、全パッケージのテストが成功した。
- `gofmt -l cmd internal tests`に未整形ファイルはなく、`git diff --check`も通過した。

総合E2EはCGOを無効にしてビルドしたCLIを別プロセスから実行した。JSON加工と保存、引数・環境変数・cwd、ネストした相対importとtop-level await、HTTPのGET・POSTと保存、開始済みI/Oの完了待ち、エラー診断と失敗終了、明示終了を確認した。READMEに載せたHello World・JSON加工・HTTP取得の実際のサンプルも検証した。HTTPにはローカルテストサーバーを使い、外部サービスはテストの前提にしていない。

文字列などを直接throwした際のスタックはエンジンから取得できないため、実行元の名前とメッセージを表示する。通常のErrorと構文エラーでは、エンジンが提供する位置・スタックを表示する。
