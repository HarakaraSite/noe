# NOE インクリメント2 REPL実装計画

インクリメント2では、Goで小さなREPLを実装する。同じランタイムでJSを繰り返し評価し、変数や関数を保持したまま、ファイル・HTTP処理を対話的に試せるようにする。

状態は完了。全4スライスの実装・テスト・レビューと、既存CLIを含む総合E2Eを完了した。前提は、インクリメント1の実装コミット`e82d643`と、[MVP案](mvp.md)のREPL方針。

## 対象範囲

- `noe repl`で起動する。
- 1行ごとにJSを評価し、式の結果を表示する。
- 変数・関数・オブジェクトを入力間で保持する。
- 構文エラー、実行エラー、未処理のPromise rejectionを表示し、次の入力を受け付ける。
- 既存のconsole、`noe`、HTTPサブセットを使う。
- `await`式と単一変数の非同期初期化を扱う。
- EOF、`noe.exit(code)`、Ctrl+Cで終了する。

履歴、補完、専用の行編集、複数行入力、自動インデント、TypeScriptは今回の対象外とする。npm対応、Node/Deno互換は引き続き実装しない。既存の`run`・`eval`のESモジュール実行仕様を維持する。

## 操作と評価の契約

| 項目 | 動作 |
| --- | --- |
| 起動 | `noe repl`。引数なしの`noe`は現在どおりhelpを表示する |
| 入力 | 標準入力から1行ずつ読む。空行は評価しない。EOF直前の改行なし入力も評価する |
| プロンプト | `> `を標準出力に表示する。パイプ入力でも同じ表示とし、専用の端末判定は追加しない |
| 通常の評価 | 同じランタイムのスクリプトとして評価する。`let`・`const`・関数などの状態を保持する |
| 結果表示 | `undefined`は表示しない。他の値はconsoleと同じ整形方法で表示する |
| オブジェクト式 | `({ value: 1 })`のように括弧で囲む。文と式の解釈はJSの構文に従う |
| 非同期 | 明示的な`await`で結果を待つ。各入力で開始したI/Oと後続のJS処理を処理してから次のプロンプトへ進む |
| エラー | 通常のJSエラーは標準エラーに表示し、状態を保持して続行する。実行済みの変更を巻き戻さない |
| 引数とパス | `noe.args`は空配列。ファイル操作と入力内の相対動的importは起動時のcwd基準 |
| モジュール | `await import("./helper.js")`を使える。入力行の静的`import`・`export`は今回の対象外 |
| 通常終了 | EOFで終了コード0。途中の回復可能な入力エラーでEOFの終了コードを変更しない |
| 明示終了 | `noe.exit(code)`でセッションを終了し、指定したコードを返す。既存の停止仕様を維持する |
| 割込み | Ctrl+Cはセッション全体を終了し、コード130を返す。評価だけを中断して再開する動作は後から検討する |
| 続行不能な失敗 | 入力読み取り失敗、エンジン内部エラー、要求していないランタイム終了は診断してコード1で終了する |

通常の式がPromiseを返しただけの場合、暗黙に結果値へ変換しない。値の表示はconsoleの整形に従い、解決結果を使う場合は明示的に`await`する。

想定する使い方は次のとおり。

```text
$ ./noe repl
> let count = 1
> count += 1
2
> const text = await noe.readTextFile("examples/data/sales-day-1.json")
> const orders = JSON.parse(text)
> orders.length
4
> const sales = await import("./examples/lib/sales.js")
> sales.summarizeSales(orders).totalRevenue
3100
> noe.exit()
```

## 既存実装からの変更方針

現在の`runtime.Execute`は実行ごとにランタイムを作り、ESモジュールの評価後に閉じる。そのまま繰り返す方式では入力間の状態を保持できないため、REPL用のセッションを追加する。

- `internal/runtime`で、ホストAPIの導入、ローカルモジュール読み込み、ジョブ処理、診断を再利用する。
- セッションの生成・1入力の評価・結果の整形・終了を分ける。JSの値はセッション内部で扱い、CLIには表示用の結果と終了状態を渡す。
- `internal/cli`に入力用の`io.Reader`を渡せるようにし、`cmd/noe`から`os.Stdin`を接続する。
- 入力ごとの失敗と未処理rejectionを、その入力の診断として消費する。前のエラーで次の入力を失敗扱いしない。
- 通常のJSエラーでも、その入力で開始したI/Oを処理してから次へ進む。明示終了とセッション割込みでは停止を優先する。
- JSランタイムは評価ループのgoroutineだけが操作する。入力待ちの割込みに別goroutineを使う場合、その役割は入力の読み取りと通知だけにする。
- consoleの内部整形関数をホスト側で保持し、結果表示にも使う。公開consoleは現在の3メソッドのままとする。

汎用プラグイン層、複数エンジンへの抽象化、独自のイベントループ製品は作らない。

## 非同期入力の実装方針

固定したgo-quickjsの通常スクリプト評価は、top-level awaitを直接受け付けない。一方、async関数のPromiseを待ち、結果を通常のスクリプト評価で変数へ結び付けることはできる。

今回の対応範囲は、`await expression`と、`const name = await expression`・`let name = await expression`・`var name = await expression`の単一変数初期化とする。通常の同期入力はそのまま評価する。非同期入力の分割代入、複数変数宣言、複数文を含む一般的なソース変換は今回は対象外。

非同期の初期化結果を待ってから、元の宣言種別でセッションに変数を作る。`const`を単なるグローバルへの代入に書き換えて、再代入できる状態にしない。既存の変数への`await`結果の代入は、通常の代入式として扱う。

この二段階の初期化では、同名の`const`・`let`が既にある場合も、右辺のI/Oを実行した後に重複宣言を診断する。通常の宣言とは検査の順序が異なる。実行済みの書き込み等を巻き戻さない。

入力の認識と変換は小さな対応範囲に限定する。単語としての`await`が文字列・コメントに出ただけで非同期変換しない。未対応の宣言形式や複数文を誤って別の意味で実行しないよう、変換前に構文を確認する。エンジン内部のparserを直接取り込んだり、独自のJSコンパイラーを実装したりしない。

async評価のPromiseには、ジョブ処理が走る前に失敗処理を接続し、同じ失敗の二重報告を防ぐ。初期化が失敗した場合は変数を新たに作らず、次の入力へ進む。解決源のない未完了Promiseは`ErrNeverSettles`として診断する。

スライス2では、エンジンの`CheckSyntax`で非同期式とカンマ位置の構文を確認する方式を採用した。文字列・コメント・正規表現・テンプレート内のカンマと、複数宣言の区切りを区別し、未対応の入力を実行前に診断する。値はJSON等へ変換せず、同じランタイムの値として変数へ結び付ける。エンジン変更や追加のparser依存は必要としなかった。

## スライス1 セッションと同期評価

同じランタイムを使うセッションと、1入力の評価・結果表示を作る。

- ホストAPIを一度だけ導入する。
- 通常のスクリプト評価で変数と関数を保持する。
- consoleの整形方法で値を表示し、`undefined`は省略する。
- 入力を識別できるソース名を付け、診断を維持する。
- 入力ごとのJSエラーと未処理rejectionを消費し、次の評価へ持ち越さない。

完了条件は、`let count = 1`・`count += 1`・`count`が順に動き、関数とオブジェクトも保持できること。構文エラーと実行エラーの後に、同じ変数を再び使えること。配列・オブジェクトを読める形式で表示できること。

## スライス2 非同期評価とホストAPI

非同期入力の対応範囲を検証してから、セッションへ接続する。

- 明示的な`await`、単一変数の非同期初期化、既存変数への代入を提供する。
- `const`の再代入禁止と、`let`・`var`の更新可能性を維持する。
- ローカルの動的importと、既存の非同期ファイル・HTTP APIを使えるようにする。
- 入力で開始したI/Oと後続のJS処理を待ち、未処理の失敗をその入力で報告する。

完了条件は、`const text = await noe.readTextFile(...)`の結果を次の入力で使い、JSONを加工して保存できること。HTTPと動的importも次の入力へ値を保持できること。初期化失敗・未処理rejection・解決源のないPromiseの後に続行でき、未対応の入力を別の意味で実行しないこと。

## スライス3 CLIと終了処理

`noe repl`を接続し、入力・プロンプト・終了を扱う。

- 標準入力の行を読み、同期・非同期評価へ渡す。
- 空行、EOF、改行なしの最終行を扱う。
- EOFと`noe.exit`の終了コードをCLIへ返す。
- 入力待ち・評価中・HTTP待ちのCtrl+Cでセッションを終了する。
- 既存の`run`・`eval`・help・versionと引数なしのhelp表示を維持する。

完了条件は、標準入力を与えた連続評価と実ターミナルでの基本操作が動くこと。`noe.exit(0)`・非ゼロ終了・EOF・Ctrl+Cを確認し、終了後のJSを実行しないこと。

## スライス4 利用説明と総合E2E

READMEにREPLの使い方と対応範囲を記載し、ビルドしたCLIを別プロセスから通して検証する。

- 複数入力にまたがる状態保持と、エラー後の続行を確認する。
- ファイル読み込み・JSON加工・HTTP・保存を対話入力として実行する。
- 入力ごとのI/O完了、明示終了、EOF、割込みを確認する。
- インクリメント1のE2Eも通し、ファイル実行の振る舞いを維持できていることを確認する。

完了条件は、READMEの対話例が動き、REPLと既存CLIの総合E2Eが成功すること。

## 検証とレビュー

各スライスで目的に対応するテストとレビューを行い、未解決の必須指摘を処理して次へ進む。JSの言語適合性やNode/Deno互換性を検証対象にしない。

実装中は変更した機能を絞って確認する。スライスの区切りで`go test ./...`とCGO無効のビルドを行う。非同期セッションと入力待ちのgoroutineを変更した場合は、関連するruntime・CLIのrace検査を行う。

最後に`go test -tags=e2e ./... -count=1 -v`を実行する。E2Eは複数行の標準入力をCLIへ渡し、標準出力・標準エラー・終了コード・保存ファイルを検証する。HTTPはローカルサーバーを使う。パイプ入力のE2Eに加えて、実ターミナルでプロンプトとEOF・Ctrl+Cの操作を確認する。

## 計画時点の確認

固定したgo-quickjsで、通常評価の変数保持、JSエラー後の続行、async関数のPromise完了待ち、待った結果を`const`へ結び付けて次の評価で参照する方法、`const`への再代入失敗を確認した。これはエンジンAPIの小さな検証であり、REPL製品の実装・テスト完了を意味しない。

## 実装とレビューの結果

| スライス | 実装と検証 | レビュー |
| --- | --- | --- |
| 1 | セッション・状態保持・結果整形・エラー回復を実装。GoテストとCGO無効ビルド成功 | 整形中の明示終了、複数エラー診断のP2二件を修正。再確認で解消済み |
| 2 | 非同期入力・宣言・動的import・入力ごとのI/O処理を実装。GoテストとCGO無効ビルド成功 | 整形中のキャンセルのP2を修正。再確認で解消済み |
| 3 | REPLコマンド・入力・EOF・終了・割込み経路を実装。GoテストとCGO無効ビルド、CLIのrace検査、PTY操作の確認が成功 | 次へ進める。必須修正なし |
| 4 | READMEと独立したCLI E2Eを作成。REPL・既存CLIの総合E2EとREADMEの対話例が成功 | 次へ進める。必須修正なし |

スライス1・3は通常レビュー、スライス2・4は批判的レビューを実施した。以下のP2三件を修正し、変更箇所と既存指摘に限定した一回の再確認で解消を確認した。

| 指摘 | 修正 |
| --- | --- |
| 結果整形中の明示終了が指定コードを返さない | 整形中の`ErrClosed`も終了要求と対応させ、指定したコードを返す |
| 同じ入力に含まれる複数エラーの一部が表示されない | 結合・ラップされたエラーを個別に整形し、各診断を保持する |
| 結果整形中のgetterが入力のキャンセルを引き継がない | `CallContext`で整形し、入力contextのキャンセルを適用する |

通常の入力終了と整形終了の両方でI/O・ジョブと未処理rejectionを処理する。非同期宣言の一時値の後始末にも入力contextを渡す。未解決の必須指摘はない。

## 総合検証の結果

Go 1.27.2、Linux amd64環境で以下の検証が成功した。

- スライス1〜3の`go test ./...`とCGO無効のCLIビルド。
- `go test -race ./internal/runtime ./internal/cli`。
- スライス4の独立したREPL E2Eと、READMEの対話例の実行。
- 全スライスのレビュー後の`go test -tags=e2e ./... -count=1 -v`。REPLとインクリメント1の全テストが成功。
- `gofmt -l cmd internal tests`と`git diff --check`。未整形ファイル・空白エラーなし。

REPL E2Eは別プロセスの連続入力・標準出力・標準エラー・終了コード・保存ファイルを確認した。変数と関数の保持、非同期宣言とconstの再代入禁止、ファイル・動的import・ローカルHTTP、エラー後の続行、未対応の入力で副作用を起こさないこと、I/Oの完了待ち、重複宣言の右辺実行順、明示終了、改行なしの最終入力を検証した。

実際のバイナリをPTYで操作し、Ctrl+Dのコード0、入力待ちと無限ループ評価中のCtrl+Cのコード130を確認した。HTTP待ちのSIGINTはローカルサーバーとCLIプロセスのE2Eで、コード130と通信のキャンセルを確認した。シグナルの送信前にはプロンプト・評価開始ログ・HTTP開始を待つ。外部サービスはテストに使わない。

リポジトリ直下の`noe`も最新ソースでCGOを無効にしてビルドした。`./noe repl`で対話実行できる。
