# NOE v2.7.0

This feature release isolates failures of registered agent hooks and makes them
available to the task through normal model requests and retained outcomes.
Go 1.27.2, official go-quickjs v0.28.0 and all other dependencies are unchanged.

## Important behavior change

**Throwing from a registered hook no longer stops the task. Hooks are not an
approval or execution-veto mechanism.** In particular, a failed `beforeTool`
does not skip the tool: execution continues with the last valid arguments.
Review hooks that previously relied on throwing to prevent execution before
upgrading. No compatibility switch or new approval/skip API is introduced.

Configuration validation, module resolution/loading and invalid handler exports
remain task-preparation errors. Cancellation, existing execution limits and
non-recoverable scope/Host failures still use their normal termination paths;
they are not converted into recoverable hook warnings.

## Hook-local recovery

- Ordinary exceptions, rejected promises and replacement-value validation errors
  in `beforeModelRequest`, `afterModelResponse`, `beforeTool` and `afterTool`
  fail only that invocation. Later hooks and the task continue.
- Successful earlier argument/result replacements and image selections are
  preserved. Completed file operations, runtime information and other side
  effects are not rolled back or automatically repeated.
- An `afterTool` failure preserves the last valid tool result and images.
  A recovered failure does not cancel sibling parallel tools or disguise the
  tool's actual success/failure.

## Notification and retained results

- The existing `hook.failed` observation event remains available. Run-owned
  failure records also work when JSONL/event-file recording is disabled.
- Pending failures are facts in the existing `NOE_CONTEXT_STATUS` message,
  not human guidance or repair instructions. A before-model failure accompanies
  that request; later failures accompany the next normal request if there is one.
- Notifications are included in context preparation and estimates. Only the
  invocation batch admitted with an actual provider request is marked notified;
  context reads, preparation and steer-only re-preparation do not consume it.
- **A hook failure alone never forces another model request or delays final
  completion.** A final-response hook can fail while the task still completes.
  The model is not guaranteed to read failures that occur after its final reply.
- Optional `TaskOutcome.hookFailures` retains recovered failures, including
  `invocationId`, phase/module/index, source model/tool identifiers, error text
  and optional `notifiedRequestId`. A completed task can have hook failures.
  The field is omitted when empty and is separate from the answer and main error.
- JavaScript and public Go clients expose the same records through `lastResult`,
  observation, `wait_task` and `wait_tasks`. `includeAnswer: false` preserves
  hook metadata; `read_task_result` still returns only the original answer.
  A later keepAlive task does not receive an old task's pending failures as
  new notifications or mutate its retained outcome.
- Error descriptions may include paths, command output or user data and can be
  sent to the model and retained. Automatic redaction is not provided.

## Validation and distribution

Implementation validation passed full unit and local E2E suites, race checks
for the four affected packages, vet, changed-JavaScript lint, public declaration
checks, formatting and diff checks. Normal and critical reviews have no
unresolved P2-or-higher finding.

Real executor fixtures cover all four phases, valid replacements/images,
parallel tools, delivery and retention, steer re-preparation, trim, queue
lifetimes, cancellation and execution limits. The final hook failure does not
create an extra model request. CLI fixtures also verify recovery without an
event file and observation of hook failure followed by normal completion.

Release preparation reuses those results. The unchanged lightweight CI builds
six binaries, generates SHA256SUMS and publishes the immutable tag.
Native execution verification is Linux amd64; other targets receive build and
checksum verification. No paid model-provider call is required.
See the [release checkpoints](release-checkpoints.md).
