# NOE v2.0.1

This patch makes human queue/steer instructions visible in observation output
and adds a runnable resident Go embedding example. CLI commands and public
JavaScript/Go API arguments and return values remain unchanged. Go 1.27.2,
go-quickjs v0.27.0 and provider dependencies are unchanged from v2.0.0.

## Observe human control instructions

- `--observe` and `noe observe` show the original instruction once when a
  `noe queue` or `noe steer` command is accepted. Multiline text, indentation
  and Markdown syntax are preserved as plain input, not formatted as an agent
  response.
- Human queue completion/failure/cancellation and steer application/cancellation
  show status and command ID without repeating the instruction. Acceptance is
  not proof of task start or steer application.
- Initial tasks and internal queues stay hidden in the human view. Existing
  internal steer status lines remain available. Saved-log playback uses the
  same renderer; older logs without instruction text remain readable.

The additive `instruction` field is recorded on queue/steer
`command.accepted` events, including initial tasks and commands from
JavaScript/Go APIs. Later states do not repeat it. **Instructions may contain
sensitive information:** consider terminal sharing and JSONL access/retention.
Missing text in older logs cannot be reconstructed. See
[observation](../observe.md) and [event fields](../events.md).

## Resident Go embedding example

[examples/embedding-server](../../examples/embedding-server/README.md) keeps a
Go HTTP host running and creates a fresh `stdlib.Execute` runtime, environment
and output buffers per request. It demonstrates request deadlines and
cancellation, SIGINT/SIGTERM shutdown with cleanup waiting, a copy-out Go module
template, and Linux systemd user-service setup/logging/stop commands.

No NOE CLI process, agent Host, credentials or external service is needed.
The example executes fixed Go-owned JavaScript, not client-supplied scripts.
It is a local demonstration without authentication, persistence or production
resource controls. systemd management does not make it a production service.

## Validation

The focused implementation checks cover real CLI queue/steer acceptance while
the provider is blocked, plain multiline display, ID-only later statuses,
hidden internal queues, and live/saved-log equivalence. The embedding example
has request-isolation, deadline, cancellation and shutdown/cleanup tests;
a built binary was checked for HTTP responses and clean SIGTERM exit.
The systemd unit was syntax-checked; an installed user service and long-term
continuous operation were not tested.

Release gates and publication/download evidence are recorded separately in the
[release checkpoints](release-checkpoints.md). Native execution is checked on
Linux amd64; other distribution targets have compilation/build evidence.
