# NOE v1.11.0

NOE adds `noe:http` as the recommended HTTP entry point and streams outgoing request bodies without collecting them in full. Scripts, Workers, and agent `run_js` processes use the same maintained implementation.

## HTTP entry point and upload streams

```js
import { fetch, serve } from "noe:http";

const response = await fetch(url, {
  method: "POST",
  body: ReadableStream.from([
    new Uint8Array([0, 255]),
    new Uint8Array([17, 34]),
  ]),
});
console.log(await response.text());
```

The module exports the same `fetch` and `serve` function values as their globals. Existing globals, `node:http`, and the `http` alias remain available. Request, Response, Headers, Web Streams, and WebSocket integration share the existing types and implementation. No new dependency or Node.js compatibility layer is introduced.

Outgoing ReadableStream bodies must yield Uint8Array chunks. NOE forwards one chunk at a time, waiting for its handoff to the HTTP transport before reading the next. Offset views and empty chunks are supported. The bridge does not buffer the whole upload; source queues, clone/tee branches, transport buffers, and operating-system buffers remain separate.

Abort signals, client timeouts, producer failures, runtime shutdown, and Worker termination stop uploads and release owned IO. When final response headers arrive before upload EOF, NOE stops the unfinished upload while leaving the response readable. The default 30-second client timeout includes upload and response-body reading.

## Body ownership and compatibility

Request bodies are consumed once. Passing a Request to fetch preserves its body and consumes the selected body. Constructing a Request from another unused Request transfers that body; use `clone()` explicitly before consumption when two branches are needed. Used or locked bodies are rejected. A pre-aborted signal rejects before acquiring or transferring the body.

Stream bodies are not replayable: 307/308 redirects that require resending them are returned as responses. The host client can follow 301/302/303 with a bodyless request. Finite string/byte bodies retain the existing known-length and replay behavior.

The server still buffers incoming request bodies up to its existing read cap before invoking a handler. Incoming request streaming and general full-duplex HTTP are not provided in this release. The existing 32 MiB response read cap still returns that prefix and ends normally; it is not an upload-size limit. Go hosts installing Fetch without a Loop retain synchronous finite-stream buffering.

## Documentation and validation

Bundled English documentation is available through `noe docs noe:http`, `noe docs noe:http fetch`, and `noe:docs`. A [finite upload example](https://forge.harakara.site/littleisland/noe/src/tag/v1.11.0/examples/http/upload-stream.js) supports a loopback echo or a supplied URL and optional response file. Existing docs topic/member IDs and the 26 Node-style modules are unchanged.

The [HTTP entry-point record](https://forge.harakara.site/littleisland/noe/src/tag/v1.11.0/docs/development/stdlib-step3-http-implementation.md) and [upload-streaming record](https://forge.harakara.site/littleisland/noe/src/tag/v1.11.0/docs/development/stdlib-step4-upload-implementation.md) include incremental-arrival and backpressure checks, cancellation and early-response tests, main/Worker/agent integration, unit tests, race detection, CLI E2E, vet, and six-target compilation. Independent review findings were corrected and re-reviewed with no remaining P2-or-higher issues. A real-provider basic upload task completed after its concurrent POST/ACK instructions were clarified; the initial failure is retained in the record.

Downloads cover Linux, macOS, and Windows on amd64 and arm64, with `SHA256SUMS`. Native execution is verified on Linux amd64; other targets have compilation evidence.
