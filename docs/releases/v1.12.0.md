# NOE v1.12.0

HTTP servers now receive request bodies incrementally. A handler starts after headers arrive and can process `request.body` before the sender reaches EOF. Scripts, Workers, and agent `run_js` processes share the same maintained implementation.

## Incoming request streams

```js
import { serve } from "noe:http";

const server = serve({ port: 0 }, async request => {
  let byteCount = 0;
  if (request.body !== null) {
    for await (const chunk of request.body) byteCount += chunk.byteLength;
  }
  return Response.json({ byteCount });
});
console.log(server.url);
```

Incoming bodies yield Uint8Array chunks. The bridge reads only on JavaScript demand, with a zero high-water mark, at most one native read in progress, and a maximum read size of 32 KiB. It does not collect the whole body before dispatch. Transport, operating-system, user-source, and clone/tee buffers remain separate from that bound. Body convenience methods such as `text()` and `json()` still collect the bytes the caller asks to consume, using the shared one-shot Request rules.

GET and HEAD requests have no JavaScript body. Other requests have a null body when the host knows no body is present; an unknown-length empty request is an empty stream. The existing default 32 MiB receive cap still returns that prefix and ends normally, without an extra-byte overflow check or automatic 413 response. The original Content-Length header remains unchanged. This cap is distinct from the fetch response-body cap.

## Early responses and cleanup

A handler may respond without consuming all incoming bytes. A response stream may also consume `request.body` while it is being sent. Input remains available through response production; remaining input is closed when response sending succeeds or fails. Cancelling the input stream stops further demand without cancelling response production. An already-blocked native read can be physically interrupted when the response finishes.

HTTP/1 responses with unread input do not promise connection reuse. Accepted `Expect: 100-continue` requests receive the interim response before body reads. Final-header flushing, response-pump demand, and cancelled input reads are ordered to avoid Go HTTP drain and body-lock waits. The pump gate does not control a user source's `start()` or eager pulls: already-started reads can still need bytes, EOF, or explicit cancellation before the first final-response flush.

`server.close()` remains synchronous and idempotent. It stops admission, waits up to five seconds for graceful shutdown, then force-closes remaining HTTP connections. Runtime shutdown and Worker termination have an independent force-close path that releases listeners and pending input IO. WebSocket upgrades retain their existing socket ownership and cleanup.

General full-duplex HTTP is not guaranteed. In particular, NOE fetch still stops an unfinished upload when final response headers arrive. Existing fetch/serve globals, `node:http`, and the `http` alias remain available; their function identity, Web types, exports, and permissions are unchanged. No dependency or new JavaScript option is added.

## Documentation and validation

Bundled English docs are available through `noe docs noe:http serve` and `noe:docs`. The [finite receive example](https://forge.harakara.site/littleisland/noe/src/tag/v1.12.0/examples/http/receive-stream.js) reads and aggregates a binary request without an external service or fixed port.

The [implementation record](https://forge.harakara.site/littleisland/noe/src/tag/v1.12.0/docs/development/stdlib-step5-receive-implementation.md) covers independent-client barriers proving prefix arrival before EOF, native-demand counting, early responses, Expect variants, cancellation and shutdown, main/Worker/agent integration, full unit/race/E2E/vet checks, and six-target compilation. Independent review findings were corrected with no remaining P2-or-higher issues. A real OpenCode Go / `deepseek-v4.1-flash` agent spontaneously consulted the bundled docs and completed incremental receiving, result verification, file saving, listener closure, and a final answer in one basic task.

Downloads cover Linux, macOS, and Windows on amd64 and arm64, with SHA256SUMS. Native execution is checked on Linux amd64; other targets have compilation evidence.
