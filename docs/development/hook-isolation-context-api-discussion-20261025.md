## 1. 議論の中心と、説明の修正

### 利用者が示した方向

- hookは、所定のタイミングで任意の処理を行う仕組み。モデルの出力検査・実行許可判定に限定しない。
- **hookの例外はhookに閉じ込め、hookの処理失敗だけを理由にtask全体を終了させたくない。**
- **失敗は黙って捨てず、taskへの通知にしたい。** 観察ログへの記録だけで終わる、という意味ではない。
- 例として、ファイルへ書き出すhookで保存先が使えなかった場合、保存失敗をtaskへ知らせて、task自体は継続できるようにしたい。

書込みAPIによってはファイル自体がなくても新規作成できる。具体的な失敗例としては、保存先ディレクトリがない、既存ファイル専用のopenで対象がない、といった場合を想定できる。論点は特定のファイルAPIではなく、付随処理の失敗を本体へどう伝えるかにある。

### 議論中に修正した捉え方

当初のassistantの提案は、`beforeTool`に実行見送り用の戻り値（仮称 `skip`）を追加し、例外はtask失敗のままにするものだった。
しかし、それではhookを検査器として捉えすぎており、一般的なhookの失敗の扱いを改善できない。

利用者はCodex等の実行前確認を例として挙げたが、**NOEへの承認機能の追加を希望したのではない。**
また「検査が通った／問題を見つけた」という分類に限定しないよう指摘した。
ログ保存、外部通知、状態更新、情報の追加・加工など、モデルの判断とは独立した処理も対象になる。

`throw`そのものを禁止する話ではない。通常のJS処理として例外やPromiseのrejectは発生する。
主な見直し対象は、**NOEがhookから出た例外を、そのままtask全体の失敗へ波及させる現在の契約**である。

## 2. 確認した現行hookの挙動

| hook | 呼ばれる段階 | 捕捉されずに例外が出た場合の現行挙動 |
| --- | --- | --- |
| `beforeModelRequest` | モデル要求の準備中 | モデル要求へ進まず、task失敗 |
| `afterModelResponse` | モデル応答の取得後 | その応答のtool実行・回答確定へ進まず、task失敗 |
| `beforeTool` | 対象toolの実行前 | 対象toolを実行せず、task失敗 |
| `afterTool` | 対象toolの実行後 | 対象toolが成功済みでも、task失敗 |

モデル前後のhookの戻り値は使わない。tool前後のhookは、変更なしのほか、引数・モデル向け結果等の置換を返せる。したがって現行APIは通知専用ではないが、それをhook一般の目的と混同しない。

共通のhook実行処理は、失敗を記録したあと例外を再送出する。taskループまで例外が伝わってtaskが失敗する。
同じphaseの登録一覧は順に処理するため、途中で例外が出ると、そのphaseの後続hookも呼ばれない。
moduleの読込み失敗や、置換値の契約違反も、現状はtask失敗につながる。

`afterTool`の失敗時は取得済みの元結果を記録するが、モデル向け結果は利用不能として扱い、taskは継続しない。
既存の `TestHooksFailurePreservesExecutedResultAndCancelsParallelTool` は、実行成功したtoolの元結果を保持しつつ、task失敗と並列toolの取消しが起きることを期待している。

## 3. 例外局所化と通知の考え方

目指したい基本の流れは次のとおり。

```text
hookを呼び出す
  → 任意の処理を実行
  → 失敗したら、そのhookの例外として捕捉
  → 失敗を記録し、taskへ通知
  → taskを継続
```

hookの完了を `await` することと、例外をtaskへ波及させることは別問題。
局所化のためにhookを待たずに実行する方式へ変える必要はない。

議論で挙げた扱いの案は次のとおり。詳細な契約は未決定。

- 通知は「保存は完了していない」などの事実を示す。必ず修復・再試行せよという命令にはしない。
- taskは通知を受けて必要な判断をできるが、本来の仕事に影響しなければそのまま進められる。
- 後続hookも続行できるようにする。
- 引数・結果の置換hookが失敗した場合、そのhookの未成立の置換を採用せず、直前の有効な値を保つ案がある。
- 元のtoolや完了済みhookを自動再実行しない。実行後hookの失敗で副作用を重複させない。
- hookが途中まで行ったファイル操作などは、例外の捕捉で自動的に取り消されるわけではない。完了済みの作用と失敗を混同しない。
- task自体の取消しや、実行基盤の継続不能まで通常のhookエラーとして飲み込むことは想定しない。

**通知の具体的な形式・配送タイミングは未決定。**
モデルの次の通常要求へ渡すのか、回答確定前の失敗をどう扱うのかなどを設計する必要がある。
現行の任意phaseから使える汎用task通知APIが、すでにあるという説明ではない。

## 4. 自動コンテキストトリムの現状

現在の自動トリムは外部hookではなく、taskループとGo側のコンテキスト管理に組み込まれている。外部hookなしでも動く。

概略の順序：
準備・概算 → `beforeModelRequest` → hookによる追加情報も含めて再計算 → 必要ならトリム → 状態通知を添えてモデル要求。

- モデルwindow、応答予約、明示入力予算等から実行履歴の予算を計算する。
- テキスト量は基本的にmessages/toolsのJSON UTF-8バイト数を4で割る近似。tokenizerの実測ではなく、画像分の概算は別途加える。
- 実行履歴量が予算に達すると、古い完了ブロックを削る。モデルによる要約ではない。
- 既定の `retainRatio: 0.1` は、トリム時点の実行履歴量の約10%を残す目標。
- モデル応答と対応するtool結果等を完了ブロック単位で扱う。最新ブロックや保護対象は残すため、厳密に目標量まで減らせるとは限らない。
- system、元の依頼、追加指示などの保護対象は削除しない。
- `contextPolicy: null` で自動トリムを無効にできる。状態通知は継続する。
- 同じkeepAlive instanceのqueue taskでは、trim後の会話とtrim状態を引き継ぐ。

Go側が削除計画を作り、JS側が履歴候補を構成し、Go側で検証・確定してからJS側にも反映する。
revision、削除対象ID、候補内容等を照合する。taskへの標準通知 `NOE_CONTEXT_STATUS` と観察用 `context.trimmed` イベントは、外部hookとは独立した経路である。

## 5. トリムをhookへ揃える可能性とコンテキスト操作API

利用者から、トリムもhookへ揃えられるかという問いと、外部へ出すならコンテキスト操作APIも必要だという指摘があった。
**外部化の可能性を検討した段階で、採用・実装範囲は未決定。**

トリムを標準hookとして実行し、利用者hookと呼出し・例外捕捉・記録・task通知を共通化する案が考えられる。
現在の外部hook APIには履歴の削除操作がないため、既存処理を外部ファイルへ移すだけでは成立しない。

外部化には二つの水準がある。

1. **実行条件や保持率を外部で決める。** たとえば仮の `api.context.trim({retainRatio: 0.1})` を呼ぶ。本体に削除選択アルゴリズムが残る。
2. **残す履歴の選択も外部で決める。** ブロックの参照と変更の適用APIを使い、外部JSが削除対象を選ぶ。

必要になり得るAPIの機能：

| 機能 | 内容 |
| --- | --- |
| 状態の参照 | 予算、概算量、履歴のrevision |
| 履歴の参照 | ブロックID、概算量、保護対象、必要に応じた本文取得 |
| 履歴変更の適用 | 指定revision・対象IDに対する変更を、整合性を保って確定 |
| taskへの通知 | 変更内容や処理失敗を知らせる。トリム以外のhookからも使える共通機能を検討 |

これらは機能案であり、API名・引数・戻り値は未決定。`api.context.trim` も未実装の例示である。
通知をコンテキストAPIに含めるか、独立したtask通知APIにするかも未決定。

外部hookが「どの履歴を残すか」を決め、本体がrevisionや保護対象、tool呼出しと結果の対応を検証して確定する分担を検討した。
標準トリムも同じAPIを使う利用例にできる一方、任意の会話全文書換えまで公開する必要があるとは決めていない。

失敗時に元の履歴で継続するには、未確定の計画だけが残って後続処理を妨げないことなど、処理の状態管理が必要になる。
適用済みの変更があれば、その後の別処理の例外で「未適用だった」と扱わない。
また、トリム失敗後に継続できても、未トリムの入力をproviderが受け付ける保証にはならない。

## 6. 現在のhook APIの登録・寿命について確認したこと

`run_agent(config, instruction, options?)` と `spawn_agent(config?, instruction?, options?)` の第1引数で指定する。

```js
// agentの起動設定の一部
hooks: ["./hooks/logger.js"]
```

- 各moduleから `beforeModelRequest`、`afterModelResponse`、`beforeTool`、`afterTool` の必要な関数を名前付きexportする。
- handlerは `(event, api)` を受け取る。モデルがhookを呼ぶのではなくNOEが呼ぶ。
- `api.context.get()` は状態参照、`setRuntimeInfo()` は `beforeModelRequest` で今回の情報を追加する操作。現行APIに履歴トリム操作はない。
- 同phaseはmodule一覧順にawaitする。異なるtool callのhook処理は並行し得る。
- 子agentは `hooks` 省略で親の一覧を継承、明示配列で置換、`[]` で解除する。親子でmodule変数を共有するわけではない。
- 登録一覧は固定。module本文と依存は各task開始時に読み込み、task中には再読込みしない。
- 同じkeepAlive instanceの次taskでもruntime・module状態は新しく、hook内変数はtaskをまたいで保持しない。
- 設定内の相対moduleパスはホストのcwd基準。hook内の相対importはそのmoduleの場所が基準。bare名にはimport mapを使える。
- `run_agent` は通常task終了・instance回収まで待つ。`spawn_agent` は受付後にIDを返す。hookの指定方法は共通。
- 起動用の `task.js`、hook用の `logger.js` は単なる例示で任意のファイル名。特別な名前なのはexportするhandler名。
- `hook("イベント名", callback)` のような動的登録APIは現在存在しない。今回その追加を決めたわけでもない。

根拠：[hookガイド](../hooks.md)、[agent API](../api.md)、[hook実装](../../internal/agent/js/hooks.js)。
