## 現状の理解

| 場所 | 主な責務 |
| --- | --- |
| `stdlib/` | 公開Go APIとしての汎用JavaScriptランタイム・標準API |

## 2. 既知のengine不具合を追跡する

### 確認した事実と影響

ES module直下の`try`などのブロックで宣言した関数が見えなくなる既知の問題がある。
今回も、次の形で`ReferenceError`になることを現在の実行環境で再確認した。

~~~js
try {
  async function worker() { return 7; }
  console.log(await worker());
} catch (error) {
  console.log(String(error));
}
~~~

関数式への置換では実行できる。詳しい原因・影響範囲・既存の検証は
[依存更新の記録](dependency-updates.md#上流修正待ちes-module内のブロック関数宣言--2026-10-24)にある。
これは今回新しく発見したNOE側の退行ではなく、固定したgo-quickjs v0.28.0の既知問題である。

### 提案する範囲と維持する方針

- 利用者が決めた上流修正待ちの方針と、正式go-quickjs v0.28.0の利用を維持する。
- 修正版を取り込む際に、最小再現と外側の同名関数を誤って呼ぶケースを確認する。
- 必要な箇所では関数式による回避方法を参照できるようにする。

本書はengineのfork・依存の差し替え・自動的なコード変換・上流issue／PR提出を提案の実施範囲に含めない。
上流の最新branchやissue／PRの状態は今回確認していない。

### 修正版取り込み時の完了条件

最小再現と同名関数のケースが、NOEを通じた実行でも期待どおり動作すること。
追加の検証範囲は、取り込む実際の差分と影響経路に応じて決める。

## 3. TypeScript対応を段階的に検討する

### 確認した事実

- [既存のTS検討メモ](../future-candidates.md#typescript)には、esbuildのGo APIによる変換と外部`tsc`による型検査を分離する案がある。
- 現在の[module解決](../../internal/modulemap/snapshot.go)は`.js`／`.mjs`のみを受け付ける。
- TS変換・実行、`run_ts`への切替は未実装で、版・時期・公開契約も未決定である。

### 提案する段階

1. **ファイル実行の最小対応を決める。** 入口の`.ts`だけでなくimport先の変換、ESM／import mapの解決、module IDの整合を対象にする。
2. **診断を元のTS位置へ対応させる。** 変換成功だけでなく、実行時の失敗から元ファイルを修正できることを目指す。
3. **モデル向けtoolの変更は別に判断する。** `run_ts`の採用、`run_js`との互換、hook・履歴・イベントへの影響を整理する。

型検査は外部`tsc`やエディターに任せる案を維持し、実行前の毎回型検査や`tsc`同梱を前提にしない。
main・eval・Worker・agentのどこまで同時対応するかは、着手前に明示する。
TS対応を、npm探索・パッケージ管理・Node.js／Deno完全互換へ拡張しない。

### 採用時の完了条件

- 決定した実行経路で、TSファイルとimport先を実行できる。
- 利用者が診断から元のTS位置を特定できる。
- 対応経路の既存JS実行、取消し、資源の所有関係を維持できる。
- 変換・実行と型検査の責務、および未対応範囲が利用資料で分かる。

今回、変換器の接続実験・性能測定・互換性検証は行っていない。
実装や大規模な検証の前に、利用経路と上記の対応範囲を決める。
