## 依頼と評価範囲

利用者の明示依頼により、親が構成案を作成し、独立reviewer `v2_runtime_review` 1体へ通常レビューと批判的レビューを依頼した。会話全体は継承せず、目的・権限・正本・成功条件を限定した入力を渡した。追加agentは起動していない。

評価段階は「具体的な実装設計（段階A）へ進む構成案」。完成API、製品実装、v2公開の承認ではない。上限は初回の両観点合計30分、新しい証拠が10分なければ中断。限定再確認は変更箇所だけを1回15分以内とした。

通常レビューは現行sourceとの整合、依存方向、所有・取消し、NOE固有パスの分離、重要な抜けを評価した。批判的レビューは構成の必要性、過剰設計、代替案、移行負担、実用上の不利益を評価した。一般的な仮想リスクを理由とした機能制限や、未決事項を全て今回確定する要求は評価基準にしていない。

## 初回の結果と親の判断

**通常レビュー：必須指摘なし。段階Aへ進める。**

- 汎用層からagentへの逆依存を避け、root Hostを維持し、bridgeとHostの終了所有を分ける案は現行の接続点と整合する。
- 明示ConfigFileでも残るHOME/XDG解決、定義内の`${configDir}`・環境変数によるcredential探索、OAuth更新時の保存先を分離対象としている。ConfigFileを指定するだけでNOE依存が解消するとは扱っていない。
- 公開型、callbackの並行契約、資源別の終了順は未確定だが、段階Aの成果物として残せる。これらを決めずに製品実装へ進む判定ではない。

親もこの判定を採用する。現行の接続点と構成案を整理したものであり、実装可能性を実行試験で証明したとは扱わない。

**批判的レビュー：必須指摘なし。構成分離は目的に見合う。**

公開Executor frameworkを先に増やさないこと、内部抽出と既存RPCを再利用すること、プロセス方式の恒久保守を未決とすることは、移行の負担を抑える方向として妥当だった。

| 任意提案 | 親の採否と反映 |
| --- | --- |
| 独自の保存場所だけなら明示file sourceで足りる可能性があり、認証callbackを先に公開する必要はない | 採用。§6でfile sourceを優先し、独自store/callbackの必要性は段階Aで判断する。必要ならOAuthの取得・更新・保存を一体で設計する |
| custom Provider注入だけでは、組込みadapter内の暗黙credential探索を検出できない | 採用。§10の外部consumer受入に、組込みadapter＋ローカルHTTP fixtureによる明示credentialとOAuth更新・保存の確認を追加した |

利用者の追加質問に対応し、§6には現在の4providerの既定認証file・環境変数とその出典、およびRegistry.loadがConfigFile選択より先にHOME/XDGを解決することも明記した。

## 限定再確認

任意提案2件と追加の事実表、案内リンクだけを同じreviewerへ返した。修正後SHA-256の一致を確認し、変更箇所だけの再確認を完了した。**必須指摘・追加提案なし。段階Aへ進めるという初回判定を維持する。**

- file source優先とcallback公開の必要性判断は、批判的レビューの提案意図を満たした。
- 組込みadapter＋ローカルHTTP fixtureの受入が明記され、custom Provider注入だけで隠れた探索を見逃す点を扱っている。
- 4providerの認証file表は静的定義と一致し、Registry.loadの初期HOME/XDG解決もsourceと一致した。

## 検証と限界

親は相対リンク先の存在、差分の空白、文書と静的provider定義の対応、レビュー対象のhash一致を確認した。製品コードの変更はなく、全体test・build・実provider接続は行っていない。

未確認：実装後の具体的な終了順、各OSでの資源回収、性能、実providerでの挙動。これらは後続段階の検証であり、今回の構成案レビューで成立済みとは扱わない。公開APIの確定、プロセス方式を残す範囲、外部consumerとv2実tagの取得検証も残る。
