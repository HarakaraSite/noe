# 子の完了待ち中にsteerで親へ制御を戻す実装指示

2026-10-25。NOEへ渡す実装依頼。`AGENTS.md`とこの文書を読み、現行実装を確認して、設計・ローカル実装・関連検証・コードレビュー・結果の記録まで進めてください。API名と具体的な返却形式は未決定なので、目的と維持契約に沿って決めてください。途中の通常の実装判断について、確認を繰り返す必要はありません。

## 目的と成功条件

親agentが子の完了待ちに入っていても、人から親へのsteerを受けたら待機を抜け、親モデルがその指示を読んで対処を判断できるようにする。子の状態確認、子への追加指示、必要な取消し・停止は、制御を取り戻した親が選ぶ。

成功はsteerの受付eventを出すだけではなく、**子が未完了のまま、親の待機toolが終了し、親の次のモデル要求へ追加指示が入り、対処を続けられること**。待機解除だけでは子を止めない。

## 発生した問題と正本

発端は `.noe/events/noe-events-20261024-224429-946e65d4bb5b6f10.jsonl`。親が `run_js` 内で `Promise.all([wait_task(...), wait_task(...)])` を待つ間に、子のテストがデッドロックした。23:11:27に親への「テストがデッドロックしている」をsteerとして受け付けたが、親は待機から戻れず、利用者が23:16にtaskを停止してから再開した。テストの同期不備は修正済みで、この依頼は親へ介入する経路の改善である。

要望の正本は[次の機能候補](../future-candidates.md#未完了-子の完了待ち中にsteerで親agentへ制御を戻す--2026-10-24)。構成・所有関係は[agentの構成](agent-architecture.md)、既存の利用契約は[API](../api.md#実行中taskへの指示と停止)・[イベント](../events.md)を参照する。過去の責務整理計画の対象外指定を、この新機能への変更禁止と取り違えない。

実装を読む入口：

## 対象範囲と対象外

対象はagentの待機・steer・必要な公開APIまたは専用tool、その接続、型、内蔵docs、利用例、直接関係するテスト。現在の `wait_task` は完了結果を返す契約を保ち、追加指示による待機終了はそれと区別できる入口を有力候補とする。複数対象を一度に待つ方法も含め、最終的な形は設計で決める。

Web UIは元々exampleとして作ったものであり、`examples/agent-server`の子選択・子だけの停止・操作画面の拡張は不要。任意の実行中JSやモデル要求をsteerで強制中断する一般機構、デッドロックの自動判定・自動kill、汎用event bus、依存更新、context予算・trim方針の変更、push・リリースは対象外。配布済みバイナリを置換せず、検証用ビルドとログは `/var/tmp` 等へ置く。

## 維持する契約

1. **待機解除とtask取消しを分離する。** 親へのsteerでは待機だけを終了し、親run・所有Operation・子instance・子taskを取り消さない。子の状態や結果を偽ってcompleted/failed/cancelledにしない。親は同じtaskの続きを判断できること。
2. **返却理由を区別する。** 子の完了、親へのsteer、待機requestの取消し等を呼出し側が区別できるようにする。待機解除を成功したTaskOutcomeに見せない。既存 `wait_task`・結果の繰返し取得・結果保持・owner/権限チェックは維持する。
3. **複数の子でも親へ戻す。** 一つの待機が戻っても、残りの `Promise.all` が無期限に残る設計では目的を達成しない。待機集合全体として制御を返し、未完了の子と完了済み結果を後から正しく扱えること。
4. **steerの既存経路を使う。** 待機を起こす通知だけで指示を消費・適用済みにせず、履歴への追加と既存の適用確認を通して親モデルへ届ける。受付・適用event、commandIdによる再送の冪等性、受領順、final確定との境界を維持する。Web UI経由のsteerはoriginがscriptの場合もあるため、`origin.kind == human`だけに依存した解除条件にしない。
5. **同期と寿命を保つ。** 登録直前に受けたsteerを取りこぼさない。子の完了とsteerが競合しても結果を失わず、追加指示を最終回答の前に適用する。複数の追加指示と再待機でも通知を落とさず、適用済み通知で空振りし続けない。observer・実行・channel待ちは `Host.mu` の外で行い、終了時には待機登録とrequestを解放・joinする。
6. **toolからモデルへ戻るまで成立させる。** JSの `Promise.race` だけで外側を返し、裏に未解決のRPCを残す方法では、runtimeの終了・requestのjoinで再び止まる可能性がある。待機そのものを終え、tool結果確定→履歴checkpoint→steer適用→次のモデル要求まで確認する。並列toolやhookの既存契約も壊さない。
7. **モデルが使える入口にする。** APIだけを追加して既存の無期限待ちを選び続ける状態にしない。facts・内蔵docsと必要な利用例で、子へ委譲して親が待つときの推奨方法と、追加指示で戻ったときにtoolを終了して親へ判断を返す使い方を説明する。既存の完了待ちAPIは通常の用途で引き続き使える。
8. **待機中の余計な処理を増やさない。** 追加指示も子の完了もなければ、定期ポーリングや一定間隔のモデル呼出しを必要としない。追加指示を受けたときの親の判断は必要なモデル呼出しである。

## 進め方と検証

最初に、採用する入口、複数対象の待ち方、親runとの対応、返却理由、通知と受付公開の順序、待機解除後のOperation寿命を短い計画へまとめる。そのまま対象内の実装と検証へ進む。作業は必要な範囲で分け、委譲する場合はAGENTS.mdに従って担当pathと権限を限定する。共有状態・取消し・履歴の接続について独立コードレビューを行い、具体的な利用経路を伴うP2以上は解消してから完了とする。

中心となる受入試験は、実providerではなく制御可能なモデルfixtureと実executorを使う。親が複数の子を待ち、子をchannelで未完了に保持した状態で親へsteerを送り、**子の完了を待たずに親の次要求へその指示が入る**ことを確認する。親がその後、明示的に子へ追加指示または取消しを選べる接続まで確認する。

これに加え、受付済みsteerが待機開始に先行する場合、完了との競合、複数steerと再待機、明示的な親停止・owner終了、所有範囲外のID拒否、完了結果の再取得を、変更する境界に合わせて既存試験と最小限の追加試験で確認する。タイミング任せの大量反復や網羅表を目標にしない。

関連packageのunit/fixture・変更JSのlint・gofmt・差分チェックを先に行う。最終候補で関係するrace検査と統合確認をまとめ、ソースが変わらなければ成功結果を再利用する。全体unit/E2Eは変更範囲に応じて一度行い、無関係な失敗は変更前と照合して区別する。配布先全種compileや長時間実provider検証は、この機能の動作確認だけを理由に追加しない。

テストには明示timeoutを付け、出力を実行開始時から保存する。観察callbackをchannelで止める試験では、同じobserverへ同期発行してから解除しようとして循環待ちを作らない。失敗時は短い限定再現とstackで原因を確認してから次へ進み、無期限の完了待ちに入らない。
