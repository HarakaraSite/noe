# 常駐agentのローカルWebコンソール：サンプル案

[開発記録の一覧](README.md#機能別の計画と検証記録) · [agentの観察](../observe.md) · [APIリファレンス](../api.md)

## 状態と目的

**サンプルは実装済み。本書は設計方針と完成条件を記録する。利用方法は[サンプルREADME](../../examples/agent-console/README.md)、実装詳細と確認結果は[実装・検証記録](agent-web-console-implementation.md)を参照。**

NOEで常駐するagentを起動し、ローカルURLをブラウザで開いてobserve履歴をスクロールしながら、Queue・Steer・Interruptで操作できるサンプルを作る。

画面の主役はタスクではなくagentとする。タスク一覧・タスク別詳細画面は設けない。observeの要約表示と生JSON展開を切り替える二段構成も設けず、取得内容をそのまま時系列で表示する。

## 1. 利用の流れ

1. provider・model・effortと必要な認証を設定する。
2. ターミナルでサンプルを起動する。
3. 表示されたローカルURLをブラウザで開く。
4. 入力欄からQueueへ指示を送る。
5. agentの履歴を読み、必要に応じてSteer・Interruptを送る。
6. 利用終了時はサーバープロセスを終了する。

起動例：

~~~sh
./noe run examples/agent-console/main.js
# NOE Agent Console: http://127.0.0.1:8787
~~~

- 初版は1プロセス・1 agentを対象にする。
- agentは `spawn_agent` の `keepAlive: true` で初期指示なしに起動し、最初はidleで待つ。依頼を送るまで推論しない。
- Queueの各依頼は同じagentが順番に実行し、確定済み・trim後の会話を引き継ぐ。別々の独立agentではない。
- ブラウザを閉じても、サーバーが動いている間はagentの作業と履歴記録を継続する。
- 常駐とはターミナルでプロセスが動いている間を指す。OSサービス化・自動起動は初版に含めない。
- サーバー終了時は所有するagentも終了・回収される。ブラウザの切断とは区別する。

~~~text

├──────────────────────────────────────────────┤
│ 14:20:00  Observe                             │
│ {                                            │
│   "state": "idle",                            │
│   …                                          │
│ }                                            │
│                                              │
│ 14:20:10  Queue受付                           │
│ サンプルの構成を調べて                        │
│                                              │
│ 14:20:11  Observe                             │
│ {                                            │
│   "state": "running",                         │
│   …                                          │
│ }                                            │
│                                              │
│ 14:20:30  Steer受付                           │
│ 起動方法を中心に見て                          │
│                                              │
│ 14:20:45  結果                                │
│ 調査結果は……                                 │
├──────────────────────────────────────────────┤
│ 指示を入力…                                  │
│ [Queue] [Steer] [Interrupt]       [全停止]     │
└──────────────────────────────────────────────┘
~~~

図の省略記号は説明用であり、実際のobserve表示を要約・省略する仕様ではない。

### ヘッダー

agent名、現在の状態、Queue件数、モデル情報を表示する。過去の履歴を読んでいる間も、ヘッダーには最新状態を示す。

### スクロール履歴

- agent単位で、Observe・操作・結果を同じタイムラインに並べる。runが切り替わっても同じ画面を使う。
- 各レコードに時刻と種別を付け、スナップショット・操作記録・結果の出所を区別する。
- observeは通常のJSON整形程度でそのまま表示する。独自の要約、差分だけへの置換、折りたたみ式の生JSON欄は付けない。
- 操作指示と回答の本文は元の内容を保持する。追加のLLMによる要約は行わない。
- 末尾を見ている間は新着へ自動追従する。
- 上へスクロールして過去を読んでいる間は追従を停止し、「新着○件／末尾へ」を表示する。
- 過去の読み込みや表示範囲の入れ替えで、読んでいる位置を不用意に動かさない。

### 固定の入力・操作欄

指示入力欄と操作ボタンを画面下部に固定する。Queue件数と受付記録は表示するが、独立したタスク一覧や並べ替えUIは作らない。

## 3. 操作とNOE APIの対応

| 操作 | API | 意味 |
| --- | --- | --- |
| Queue | `queue_agent({agentId, instruction, commandId?})` | 次の依頼を送る。idleなら実行開始、実行中なら順番待ち |
| Steer | `steer_agent({runId, instruction, commandId?})` | 実行中タスクへ追加指示。現在の処理は中断しない |
| Interrupt | `cancel_task({agentId, commandId})` | 対象の実行中タスクだけを中断。agentと後続キューは維持 |
| 全停止 | `stop_agent({agentId})` | agent・実行中タスク・残りのキューを停止 |

- このサンプルのInterruptは一時停止・再開や処理の巻き戻しではない。
- Steerはモデルの判断境界で反映される。受付成功を即時反映と表示しない。APIから確認できない適用状況を推測して「反映済み」としない。
- Interruptと全停止も要求受付と完了は別。最新observeやタスク結果で状態を更新する。
- Steerは送信対象のrun ID、Interruptは対象タスクのcommand IDに結び付ける。送信とタスク切替が競合しても、別の新しいタスクへ操作先を自動で変更しない。
- 実行中タスクがない場合、SteerとInterruptは利用不可とする。競合で対象が終了した場合は、その結果を画面へ返す。
- command IDは内部で管理する。タスク一覧を表示しなくても、個々の受付・結果を正しく関連付ける。
- 全停止後は停止状態と履歴を表示する。agentの再作成は初版ではサンプルの再起動で行う。

## 4. observeの取得と履歴記録

`observe_agent` は現在のlive snapshotを返すAPIで、過去のobserve履歴を自動保存するAPIではない。履歴はサンプル側で蓄積する。

### サーバー側で記録する内容

| 種別 | 内容・取得元 |
| --- | --- |
| Observe | `observe_agent({agentId, includeAnswer: false})` のsnapshot |
| 操作 | Queue・Steer・Interrupt・全停止の指示、対象ID、APIの受付結果・エラー |
| 結果 | 受け付けた各タスクの完了・失敗・キャンセル、最終回答・エラー |

- 監視はブラウザではなくサーバーで行う。観察とWeb表示の更新は約1秒間隔を初期案とする。
- 内容が同じsnapshotは重複記録せず、変化があったsnapshotを記録する。保存するsnapshot自体は差分ではなく取得した内容を保持する。
- observeでは `includeAnswer: false` を使い、直近の回答全文を各snapshotに繰り返し載せない。回答本文は「結果」として別途取得・保存・表示する。
- 各タスクは `wait_task({agentId, commandId, includeAnswer: false})` で完了を追う。保存時は `read_task_result` の `nextOffset` をたどり、`eof: true` まで回答全文を回収する。既定の1回分（4,096 bytes）だけで回収完了としない。
- 回答全文の保存と、ブラウザへの配信・表示範囲は分ける。ブラウザは保存済みの本文から必要な範囲を取得する。
- `lastResult` だけを監視して過去の結果を回収しない。後続のタスクがすぐに完了しても、各command IDの結果を取りこぼさない。
- サンプル独自のsession IDと単調増加するレコード番号を付け、再接続時の差分取得・表示順・重複防止に使う。NOEのrun IDやcommand IDとは区別する。

### 初版で保証しないこと

定期observeは状態のサンプリングであり、取得間隔より短い状態変化のすべてを記録するものではない。全ツール呼出し、生成途中の全文、thinkingなどを漏れなく表示する完全な実行イベントビューアは初版の対象外とする。保存ログの解析やCLIのobserve表示を、そのままlive snapshot取得と同じ機能として扱わない。

## 5. 履歴の保存量と画面の保持量

**保存件数と画面に一度に保持する件数を分ける。画面の都合で保存済み履歴を削除しない。**

| 対象 | 方針 |
| --- | --- |
| 保存履歴 | JSONLへ追記。件数・日数による自動削除や本文の自動切り詰めは設けない |
| 画面側の保持 | 例えば1,000レコードを初期値とし、スクロールに合わせて読み込む範囲を入れ替える |
| 古い履歴 | 上へスクロールすると保存済み履歴から追加取得できる |

- 1,000件は画面の保持量の案であり、保存上限やNOE APIの制限ではない。
- 長い回答や整形JSONは複数行になるため、「行数」ではなくレコード数で扱う。Observe・操作・結果をそれぞれ履歴レコードとして数える。
- 画面保持量の制限はブラウザの実メモリ使用量の厳密な上限を保証するものではない。
- ブラウザは必要な範囲を取得する。過去を読み進めても全履歴をDOMや配列へ積み続けず、表示範囲の入れ替えで保持量を維持する。
- サーバーも全履歴をメモリへ持ち続けず、保存ファイルを範囲取得できる構成にする。具体的な索引・読み込み方法は実装時に決める。
- 保存ファイルは増え続けるため、実際の保存可能量はディスク容量に依存する。無制限の保存容量を保証する意味ではない。
- ブラウザを開き直しても履歴を再取得できる。
- サーバー再起動後は、以前のセッションの履歴を選んで閲覧可能にする。過去セッションは読み取り専用とし、新しいagentの履歴と混ぜない。
- 以前のagent・未処理キュー・会話・実行途中の状態は復元しない。再起動後は新しいagentとセッションで開始する。
- 作業中のCtrl+Cなどによるサーバー終了では、NOEによるagentの終了・回収と、サンプルによる結果取得・JSONL保存は別である。終了時にすべての結果の取得・保存が完了することは保証しない。
- 過去セッションでは、保存済みの結果はそのまま表示する。受付記録があって結果が保存されていない依頼は「セッション終了時点で結果未記録」と表示し、完了・失敗・キャンセルのいずれかを推測しない。
- 過去のObserveは取得時点のsnapshotとして保持・表示する。最後のsnapshotが `running` であっても、過去セッションのagentが現在稼働中であるとは表示しない。

## 6. 実装構成案

~~~text
examples/agent-console/
├─ main.js          # HTTP待受、agentの所有、監視、操作・履歴API
├─ public/
│  ├─ index.html    # agent中心のコンソール
│  └─ app.js        # スクロール履歴、差分取得、操作送信
├─ data/
│  └─ sessions/    # セッションごとのJSONL履歴（実行時生成）
└─ README.md        # 設定、起動、操作、履歴保存の説明
~~~

- HTTPは `noe:http` の `serve` を使う。サーバーとagentを同じ長寿命のNOEプロセスに所有させる。
- フロントエンドは通常のHTML/CSS/JavaScript。初版ではnpm・フレームワーク・ビルド工程を要求しない。
- Web更新はHTTPポーリングとする。WebSocket・SSEは初版に必須としない。
- 起動設定としてprovider・model・effortを明示する。認証はNOEの既存設定を使い、ブラウザへ認証情報を渡さない。
- `127.0.0.1` のみで待ち受ける。ポートは8787を初期案とし、実際のURLを起動時に表示する。
- 許可するHostとOriginは、待受開始後に確定したローカルURLを基準に固定する。Originにはscheme・host・portを含め、クライアントが指定した `Host` やリクエストURLから許可値を導出しない。
- 静的ファイル・履歴取得・操作APIを含む全HTTP要求で、`Host` が許可値と一致することを検証する。ループバックへのbindだけをDNS rebinding対策としない。
- 操作APIは、`Origin` が固定した許可値と一致する要求のみ許可する。異なるOrigin、`null`、Origin欠落は拒否する。リクエストのOriginと、そのリクエストURLのOriginを比較するだけの検証にはしない。
- CORS設定だけでHost・Originの検証を代用しない。外部公開やリモートアクセスは対象外とする。
- NOEはsandboxではなく、agentは起動ユーザーのOS権限で動く。READMEに明記する。
- 履歴には指示文・回答・エラー等が保存される。機密情報が含まれ得ることと保存先をREADMEに記載し、生成データはバージョン管理に含めない。

## 7. 初版に含めないもの

- タスク一覧・タスク別詳細画面・キュー並べ替え・受付済み指示の編集。
- observeの独自要約・生JSONの展開切り替え・追加モデルによる要約。
- 複数agent管理、別プロセスで起動済みの任意agentへの接続。
- 全ツール出力や生成中全文を網羅する実行ログビューア。
- サーバー再起動をまたぐ実行再開・会話復元・キュー再投入。
- OSサービス化・自動起動・外部公開・複数ユーザー認証。
- 履歴の自動削除・ローテーション・全文検索。

## 8. 完成条件

次の利用経路を確認してサンプルとして完了とする。実装後の確認結果と検証範囲は[実装・検証記録](agent-web-console-implementation.md)に記載する。

1. 起動するとローカルURLが表示され、ブラウザから待機中のagentを確認できる。
2. Queueで依頼を送り、同じ画面でobserve履歴と最終回答を確認できる。4,096 bytesを超える回答でも全文が保存され、末尾まで閲覧できる。
3. 実行中にSteerと後続依頼のQueue追加ができ、受付内容を履歴で確認できる。
4. Interruptで対象だけを中断し、後続の依頼が実行される。全停止ではagentと残りのキューが終了する。
5. 過去へスクロール中は新着で位置を奪われず、末尾へ戻れば自動追従が再開する。
6. 画面保持量を超える履歴があっても、過去のレコードをスクロールで読め、保存履歴は削除されない。
7. ブラウザを閉じても作業・監視・保存が続き、開き直すと履歴を確認できる。
8. サーバー再起動後も以前の履歴を閲覧できるが、以前のagentやキューは再開されない。作業中にサーバーを終了し、結果が保存されていない依頼が残った場合は「セッション終了時点で結果未記録」と表示し、過去の `running` snapshotを現在稼働中の状態と混同しない。
9. 許可したHost・Originからの操作は利用できる。許可していないHostの全HTTP要求、およびOriginが異なる・`null`・欠落している操作API要求は拒否される。

約1秒の監視間隔、画面保持量1,000レコード、ポート8787を実装の既定値として採用した。ポートは起動オプションで変更できる。agent中心のUI、要約・展開切り替えなし、保存履歴を表示上限で削除しないという方針は本案の前提とする。
