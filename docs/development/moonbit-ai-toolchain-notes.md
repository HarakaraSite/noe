# MoonBitのAI向けツールチェーンからNOEへ取り入れる案

調査日: 2026-10-23。この文書は調査時点の背景と応用候補を記録する。
その後に採用した範囲、破壊的変更を含む改訂案、スライス別の実装・検証と最後の総合テストは
[AI向けコード実行契約の再設計・実装計画](ai-execution-contract-plan.md)を正本とする。製品実装は未着手。

## 参考になる考え方

コンパイラや実行環境が持つ正確な情報を、AIが必要な範囲だけ問い合わせられる形で提供する。説明を長くするだけでなく、APIを発見し、生成したコードを検査し、診断から修正する往復を短くすることに価値がある。

MoonBitの公式資料で確認した仕組みは次のとおり。

- `moon ide`は、APIの検索と説明、定義の参照、参照箇所の検索、ファイルやpackageの構造表示、意味を解釈したrenameなどを提供する。[MoonBit Agent IDE](https://docs.moonbitlang.com/en/stable/toolchain/moonide/index.html)
- `moon info`は、packageの公開インターフェースを`.mbti`へ出力する。実装全体を読む前に公開契約を確認できる。[moon info](https://docs.moonbitlang.com/en/latest/toolchain/moon/commands.html#moon-info)
- 2024年の研究紹介では、生成途中の構文・意味情報をsamplingへ戻し、不適切な生成を巻き戻す方法を説明している。同記事はトップレベルの型署名や、定義を平坦に並べやすい言語設計も論じている。これは当時の研究紹介であり、現在の全製品経路やNOEでの効果を実証するものではない。[AI-Native Language Toolchain（2024-02-18）](https://www.moonbitlang.com/blog/moonbit-ai)

## NOEへの応用候補

以下はMoonBitの機能そのものではなく、NOEへ応用する提案。
表の優先順と事前束縛の説明は調査時点のもの。採用計画では暗黙importを廃止する方向とし、
契約設計からengine・stdlib・agent経路へ順に実装する。意味を解釈したコード探索は今回の対象外。

| 優先順 | 候補 | 提供するもの | 解消したい問題 |
| --- | --- | --- | --- |
| 1 | 実行環境の自己記述 | 現在使えるmodule、export、引数・戻り値、`run_js`で事前に束縛される名前を、機械的に問い合わせられる情報 | APIやNode互換性の推測、事前束縛名の再宣言 |
| 2 | 修正につながる診断 | 安定したエラーコード、利用者コード上の位置、該当する名前、利用可能な候補、次に問い合わせる先 | エラーだけでは修正方法が分からず、同じ探索を繰り返すこと |
| 3 | 意味を解釈したコード探索 | outline、symbol検索、定義・参照箇所への移動。まず既存の言語ツールとの接続を検討する | ファイル名の推測、正規表現の失敗、大量の全体読み込み |
| 4 | 実行前の明示的な検査 | 実行系と同じparser・解決規則を利用し、実行せずに構文や束縛の衝突を検査する入口 | 実行開始後に初めて分かる生成誤り |

最初の検討対象は自己記述と診断。既存の内蔵docsを出発点に、API情報の正本を揃え、docs・型情報・検索候補を同じ情報から供給できる構成を検討する。実装済みの機械的な情報と、説明文として維持する情報は現状調査で区別する。

診断では、「docsの詳細項目がない」と「実行可能なAPIがない」を区別する。事前束縛名の衝突なら、NOEがその名前を用意していることと、再宣言を避ける方法まで分かる形が望ましい。

## 実行ログで見えた接点

観察対象は`.noe/events/noe-events-20261023-112051-325c21bec156cf76.jsonl`。以下は応用を考えるきっかけであり、NOEの回帰不具合と断定したものではない。

- seq 1847: `run_js`にNOEが事前importする`spawn_agent`を生成コードが再宣言し、束縛が衝突した。別名のmodule変数を使う次の呼び出しでは成功した。事前束縛は`docs/api.md`に説明があるが、実行時に発見しやすい情報の供給を検討する余地がある。
- seq 1831 / 5642: API自体の有無と、内蔵docsの詳細項目の有無が一致しない問い合わせで`ERR_DOC_NOT_FOUND`になった。候補や正しい問い合わせ先を返す設計と関係する。
- 存在しないファイル名・ディレクトリや、不正な正規表現を使った検索が複数回発生した。構造・symbolから探索を始められる入口が参考になる。

## 実装を検討する際の境界

- API仕様をすべて毎回のinstructionへ足すのではなく、安定した最小限の案内と必要箇所の問い合わせを組み合わせる。背景伝達量とキャッシュ効率についての既存方針に合わせる。
- MoonBitの記事でいう生成時のKVキャッシュと、NOEで観測しているプロバイダのprompt cache hit率は同じ指標ではない。MoonBitの言語設計による効果を、そのままNOEのヒット率改善として扱わない。
- NOEの現在のプロバイダ接続は、モデル内部のsamplingやtoken単位の巻き戻しを制御しない。まずは「コードのまとまりを生成 → 検査 → 診断を返す → 修正」の往復への応用を考える。
- 実行前検査で何を保証できるかは別途確認する。構文の検査、importの解決、動的なAPIの存在、実行時の正しさを同一視しない。module初期化などの副作用を起こさずに検査する境界も設計対象とする。
- 言語の置き換えや独自コンパイラの開発を前提とせず、NOE・stdlib・agentの既存の責務分離に沿って配置を決める。

効果の確認には、観測済みの衝突や探索失敗が減るか、失敗からの修正に要する呼び出し・転送量が減るかを使う。APIを推測して間違えた回数だけでなく、問い合わせ自体の費用も含めて比較する。
